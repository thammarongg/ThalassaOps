# Sprint 15 — Incident Domain and Lifecycle

**Status:** Awaiting written-spec review

**Date:** 2026-08-30

**Roadmap:** `docs/planning/sprint-plan.md`, Sprint 15

**Jira:** SCRUM-23 under SCRUM-5

## 1. Outcome

Sprint 15 turns the placeholder `Incident` contract into the canonical,
local-first incident write model. A permitted responder can explicitly create
an incident from one or more supported triggers, then move it through the
accepted lifecycle while every state change is validated, attributed and
recorded in an immutable timeline.

The exact exit criterion is:

> Incidents can be created from alerts, anomalies, user reports, scheduled
> health checks, vulnerability findings and manual reports, then progress
> through a validated state machine.

Creation is always explicit in this sprint. Replaying a signal, producing an
Operations Console queue item or forming a correlation candidate never creates
an incident automatically.

## 2. Binding decisions

1. The existing `thalassa_domain::Incident` becomes the canonical incident
   aggregate. Sprint 15 does not introduce a second incident model.
2. Current incident state is stored in a normal SQLite row. Every mutation also
   appends an immutable incident timeline event in the same transaction. Full
   event sourcing is deliberately not used.
3. Incident creation is an explicit `incident.create` write. It accepts one or
   more supported triggers chosen by the caller. Correlation candidates can
   help a caller choose related signals, but they are not incident triggers and
   never create incidents by themselves.
4. Severity is derived from a structured Business Impact assessment. A
   responder may override the derived value only with an actor and reason; the
   override is an audit event.
5. Status and disposition remain separate. A disposition never substitutes for
   a lifecycle status and never silently closes an incident.
6. Incident writes use optimistic concurrency. Every mutation supplies the
   incident version it read and fails rather than overwriting a newer change.
7. Sprint 15 supplies domain logic, persistence, secured IPC, TypeScript
   contracts and acceptance coverage. The full list/detail Incident Workspace,
   comments and interactive status controls belong to Sprint 16.
8. No live network ingestion, AI call, remediation, notification or external
   integration write is added in this sprint.

## 3. Scope

### 3.1 Included

- the canonical Incident aggregate and stable wire enums;
- six trigger kinds: alert, anomaly, user report, scheduled health check,
  vulnerability finding and manual report;
- structured Business Impact and deterministic S1-S5 severity derivation;
- the accepted status state machine, including Reopened;
- Duplicate, False Positive, Suppressed and Cancelled dispositions required by
  SCRUM-23;
- preservation of the already accepted Informational disposition;
- owning-team and responder-role assignment;
- an ordered, append-only incident timeline;
- local SQLite persistence with atomic state and audit writes;
- idempotent creation and optimistic concurrency for later writes;
- capability-, permission-, membership-, scope- and policy-checked IPC;
- deterministic fixture-backed source resolution; and
- Rust, IPC, migration and TypeScript contract tests plus end-to-end acceptance
  coverage.

### 3.2 Excluded

- automatic incident creation from replay, queue or correlation output;
- automatic grouping, merging or duplicate closure;
- a correlation candidate as a canonical incident source;
- the Sprint 16 Incident Workspace, comments and collaboration UX;
- AI investigations, hypotheses generated by a model or model egress;
- mutating infrastructure actions, action execution or rollback;
- Slack, Discord, Jira, PagerDuty or other provider-side incident writes;
- notification, escalation and response-target schedulers;
- organization-defined lifecycle extensions;
- team synchronization or a remote shared-state service; and
- provisioning.

## 4. Canonical language

### 4.1 Incident

An Incident is a correlated operational problem that a responder has
explicitly accepted into the incident workflow. It is not an alert, queue item
or correlation candidate. Those values can provide triggers and context, but
the Incident owns its lifecycle, impact, assignments and timeline.

### 4.2 Incident Trigger

An Incident Trigger records why the Incident was created. It preserves source
identity, scope, observed time and evidence references without copying a full
source payload into the incident tables.

One Incident can have multiple triggers. All triggers supplied at creation must
resolve successfully and fit the same authorized workspace and incident scope.
There is no partial creation.

### 4.3 Incident Timeline Event

An Incident Timeline Event is an immutable record of one accepted incident
mutation. It is both the responder-visible timeline foundation and the audit
record for that change. It does not replace the current-state row.

### 4.4 Incident Disposition

A disposition classifies an incident independently of its operational phase.
For example, an Incident may be Closed with a Duplicate disposition. Setting a
disposition does not cause a status transition.

### 4.5 Incident Responder Role

A responder role is an explicit responsibility held by a Principal for one
Incident. It is not a workspace membership role and does not grant permission.
Workspace membership and policy still authorize every command.

These terms are recorded in the repository `CONTEXT.md` glossary.

## 5. Architecture

```text
secured incident IPC
        |
        v
IncidentService ---------------------------------------+
  | authorize + validate + resolve triggers            |
  | apply aggregate command + append timeline event    |
  |                                                     |
  +--> IncidentSourceResolver ports                     |
  |      +--> Operations/Signal fixture projections     |
  |      +--> Sprint 13 source-record/evidence ledger   |
  |                                                     |
  +--> IncidentRepository ------------------------------+
             | one SQLite transaction
             +--> incident current state
             +--> incident triggers
             +--> current role assignments
             +--> append-only timeline events
```

The domain crate owns types, invariants, transition rules, severity derivation
and typed domain errors. The Tauri core owns source resolution, authorization,
policy enforcement, SQLite persistence and IPC error mapping. The UI contract
owns only stable serialized shapes in Sprint 15.

### 5.1 Module boundaries

- `crates/thalassa-domain`: Incident aggregate, source kinds, Business Impact,
  roles, commands, transition contexts, timeline event values and pure
  validation.
- `crates/thalassa-ipc`: stable command descriptors and capability/permission
  contracts.
- `src-tauri/src/incident`: repository, source resolver ports, fixture-backed
  resolvers and application service.
- `src-tauri/src/app/incident.rs`: IPC envelope validation, authorization,
  policy checks and error mapping.
- `src-tauri/migrations/0006_incidents.sql`: incident state, trigger, role and
  timeline persistence.
- `ui/contracts/ipc.ts` and guards: TypeScript representations used by Sprint
  16 without mounting a new workspace in Sprint 15.

No incident module reaches a provider network. Source resolver ports consume
the deterministic local values already produced by the Operations Console and
Sprint 13 replay paths.

## 6. Domain model

### 6.1 Incident aggregate

The current placeholder `Incident` is reconciled into one canonical aggregate
with, at minimum:

- `id`: UUID assigned by the server;
- `summary`: bounded, non-empty responder-facing title;
- `scope`: a workspace-contained `ResourceScope`;
- `owning_team_id`: the team accountable for the incident;
- `business_impact`: structured assessment described below;
- `severity`: current S1-S5 value plus derivation/override metadata;
- `status`: current canonical status;
- `disposition`: optional current classification;
- `duplicate_of_incident_id`: required only for Duplicate;
- `trigger_ids`, `signal_ids` and `evidence_ids`: deduplicated stable refs;
- `hypothesis_ids` and `action_ids`: retained for later sprints;
- `version`: monotonically increasing optimistic-concurrency version;
- `created_at` and `updated_at`: server timestamps.

All enums crossing IPC declare explicit Serde wire values. Incident status and
disposition use lowercase snake_case; severity retains `S1` through `S5`.

### 6.2 Trigger kinds

`IncidentSourceKind` has exactly these Sprint 15 wire values:

- `alert`;
- `anomaly`;
- `user_report`;
- `scheduled_health_check`;
- `vulnerability_finding`; and
- `manual_report`.

Alert, anomaly, scheduled-health-check and vulnerability triggers are
source-backed. Their IDs must resolve through a local projection or source
record before the write transaction begins. The resolver returns the canonical
scope, observed time, evidence IDs and, when present, signal ID and immutable
source-record digest.

A user report is structured input attributed to the reporting Principal. A
manual report is structured input attributed to the responder who chose to
open the Incident. Both use bounded fields and the same secret/credential
screening required by local incident storage. The server never stores an
arbitrary provider payload in an incident trigger.

When a user starts from a correlation candidate, the client explicitly submits
the candidate's selected underlying signals as triggers. Candidate identity may
be recorded as non-authoritative context in the creation event, but there is no
`correlation_candidate` trigger kind.

### 6.3 Business Impact and severity

Business Impact remains distinct from severity, urgency and priority. Sprint
15 expands the existing compact `BusinessImpact` representation into a
structured assessment of:

- availability;
- customer reach;
- business criticality;
- data integrity;
- security/privacy;
- financial or contractual impact; and
- trajectory.

Each dimension uses a closed typed rating. The highest-impact matching
dimension determines the initial severity. The evaluator also enforces the
accepted safety floors:

- confirmed active credential compromise, customer-data exposure or
  destructive data loss is at least S1;
- a rapidly expanding production incident with unknown reach is at least S2;
- a vulnerability is not automatically S1; exploitability, exposure, asset
  criticality and evidence of active exploitation determine its impact.

Creation stores both the assessment and derived severity. `set_severity`
either submits a changed assessment for re-evaluation or records an explicit
override with a non-empty reason. Every severity change carries actor, previous
value, new value, reason and evidence IDs in its timeline event.

Priority calculation and organization-specific response targets remain out of
scope. Existing Operations Console priority projections are not collapsed into
the canonical Incident severity field.

### 6.4 Lifecycle

The normal path is linear:

```text
Detected -> Triage -> Investigating -> Mitigating -> Monitoring -> Resolved -> Closed
```

Reopening is allowed only through:

```text
Monitoring | Resolved | Closed -> Reopened -> Investigating
```

No status may be skipped. Repeating the current status is rejected rather than
silently treated as success. The only idempotent replay is a repeated request
with the same request ID and identical stored result.

Each target status has typed transition context based on the accepted policy:

- Triage: confirmed Business Impact, initial severity, Owner and duplicate
  check;
- Investigating: bounded investigation note or hypothesis, and evidence refs;
- Mitigating: mitigation/action description, executor and expected impact;
- Monitoring: verification window, success criteria and watch owner;
- Resolved: resolution summary, supporting evidence and impact end time;
- Closed: closure notes, required follow-up references and closure actor;
- Reopened: recurrence or failed-verification reason plus new evidence or
  recurrence signal.

The domain validator rejects a structurally valid edge when its required
transition context is absent or inconsistent with the aggregate. Reopened is a
persisted status with its own timeline event; the caller then explicitly moves
it to Investigating with investigation context.

### 6.5 Dispositions

The required values are Duplicate, False Positive, Suppressed and Cancelled.
Informational already exists in the accepted policy and current domain contract
and remains supported to avoid a policy contradiction.

A disposition can be set, changed or cleared only with a reason. Duplicate
also requires `duplicate_of_incident_id`, which must resolve to another
Incident in the same workspace and cannot form a self-reference. Sprint 15 does
not automatically merge timelines, triggers or evidence and does not
automatically close either Incident.

### 6.6 Ownership and responder roles

The owning team must fit the Incident scope. Role assignments refer to existing
Principals and are separate from membership authorization.

Canonical role wire values are:

- `owner`;
- `incident_commander`;
- `technical_lead`;
- `communications_lead`;
- `approver`;
- `change_owner`; and
- `stakeholder`.

Owner, Incident Commander, Technical Lead, Communications Lead, Approver and
Change Owner have at most one active assignee each. Stakeholder can have many.
One Principal can hold multiple roles. Assigning, replacing and releasing a
role each appends an attributed timeline event.

S1 and S2 support the complete responder-role set but do not force small teams
to assign different people. Triage requires an Owner for every severity. Other
roles remain optional in Sprint 15.

### 6.7 Timeline events

The timeline is ordered by a per-Incident sequence allocated in the write
transaction, not by timestamp alone. Event kinds include:

- incident created;
- status transitioned;
- Business Impact or severity changed;
- disposition set, changed or cleared;
- role assigned, replaced or released; and
- trigger attached during creation.

Every event contains event ID, Incident ID, sequence, kind, actor ID, reason,
server timestamp, request ID, policy version and a typed payload. Mutation
events contain enough before/after data to explain the change without copying
full source payloads. Events are immutable after insertion.

## 7. Persistence

Migration `0006_incidents.sql` creates four tables.

### 7.1 `incident`

Stores current aggregate state, including identity, workspace/team scope,
serialized bounded resource scope, summary, Business Impact, severity metadata,
status, optional disposition/duplicate reference, current version and server
timestamps. The creation request ID is unique so a retried create returns the
same result.

Workspace, team and organization identifiers are stored in queryable columns;
authorization never depends on filtering opaque JSON after loading every row.

### 7.2 `incident_trigger`

Stores trigger identity and provenance: trigger ID, Incident ID, source kind,
safe source ID, optional source-record digest, scope, observed time, evidence
IDs and sanitized structured user/manual report content. A uniqueness
constraint prevents the same source identity from being attached twice to one
Incident.

### 7.3 `incident_role_assignment`

Stores assignment history with assigned/released timestamps and actors. An
unreleased row is active. Repository logic and database constraints enforce
exclusive-role cardinality while permitting multiple active stakeholders.

### 7.4 `incident_timeline_event`

Stores append-only ordered events. `(incident_id, sequence)` and request ID are
unique. SQLite triggers reject UPDATE and DELETE against this table so normal
application code cannot rewrite accepted audit history.

### 7.5 Transaction contract

Every write:

1. starts an immediate SQLite transaction;
2. loads the current aggregate and verifies workspace plus `expected_version`;
3. applies the pure domain command;
4. writes related trigger or role records when applicable;
5. updates current Incident state with `version = version + 1`;
6. appends the next timeline event; and
7. commits only when all steps succeed.

Creation inserts version 1 and the initial event sequence. Any failure rolls
back state and timeline together. Reads use a new connection following the
existing `AppState` pattern; no process-global mutable Incident cache is added.

## 8. Application flow

### 8.1 Create

1. Validate command name, `IncidentWrite` capability, `ManageIncident`
   permission, active membership and workspace scope.
2. Validate exact request shape, field lengths and request ID.
3. Evaluate local-storage and audit-retention policy before source resolution.
4. Resolve every source-backed trigger locally and screen user/manual content.
5. Reject missing, forbidden or mixed-workspace triggers as one failed request.
6. Derive canonical scope, deduplicate evidence/signal refs and calculate
   severity from Business Impact.
7. Apply the Incident creation command and persist state, triggers, initial
   roles and timeline atomically.
8. Return the canonical Incident and its first timeline page.

The resolver performs no network call. A denied or malformed trigger never
produces a partial Incident.

### 8.2 Mutate

1. Authorize the write before revealing whether the Incident exists.
2. Load by Incident ID inside workspace scope.
3. Check `expected_version` and request idempotency.
4. Validate transition or mutation-specific context.
5. Apply state and append timeline in one transaction.
6. Return the new aggregate version and accepted event.

### 8.3 Read

Read commands authorize before lookup, constrain every query by workspace and
apply UI/audit policy before returning content. Timeline pages use bounded
limits and a stable `(sequence, event_id)` cursor. Unbounded list or timeline
requests are invalid.

## 9. IPC contract

### 9.1 Permission

Add `Permission::ManageIncident`. Owner, Administrator and Operator receive it.
Viewer and Auditor do not. `Permission::Read` continues to authorize incident
reads for active workspace members.

This avoids reusing `Investigate`, which Viewer currently holds, and avoids
misclassifying an incident update as action execution.

### 9.2 Commands

Read commands require `IncidentRead` plus `Permission::Read`:

- `incident.get`;
- `incident.list`; and
- `incident.timeline`.

Write commands require `IncidentWrite` plus `Permission::ManageIncident`:

- `incident.create`;
- `incident.transition`;
- `incident.set_severity`;
- `incident.set_disposition`; and
- `incident.assign_role`.

Role replacement/release is expressed as a typed operation under
`incident.assign_role`; arbitrary JSON Patch is not accepted. Trigger
attachment after creation is excluded so all Sprint 15 trigger provenance is
fixed at creation.

Every request uses the existing `CommandEnvelope`, an unbounded envelope scope
resolved to the active workspace, a request ID, exact allowed keys and bounded
pagination. All serialized fields follow existing snake_case IPC conventions.

### 9.3 Authorization order

The handlers preserve the established order:

1. command and capability;
2. unbounded envelope shape;
3. active membership and Principal identity;
4. workspace grant;
5. required permission;
6. local-storage or UI/audit policy;
7. request shape and target lookup;
8. domain validation; and
9. persistence.

An unauthorized caller receives permission denied without learning whether a
requested Incident or trigger exists.

## 10. Validation and errors

Domain errors remain typed through IPC. Required stable error reasons include:

- invalid request shape or bounded text;
- forbidden sensitive content;
- trigger not found;
- trigger source-kind mismatch;
- trigger or Incident scope mismatch;
- empty or duplicate trigger selection;
- invalid Business Impact;
- invalid severity override;
- Incident not found within authorized scope;
- Incident version conflict;
- invalid lifecycle transition;
- missing or inconsistent transition context;
- invalid disposition or duplicate reference;
- invalid Principal, team or role assignment;
- duplicate request with conflicting content;
- policy denied; and
- persistence unavailable.

Expected validation failures never become generic internal errors. Error
details contain safe identifiers and enums, not source payloads, user report
text or secrets.

## 11. Safety and policy

- Incident state and timeline are local-storage/audit destinations and must pass
  their applicable policy checks.
- User/manual report fields are bounded structured values. Control characters,
  credential markers, tokens, private keys and sensitive account identifiers
  are rejected before persistence rather than copied into audit history.
- Source-backed triggers store only validated provenance and evidence refs; the
  post-policy source-record ledger remains the payload authority.
- Evidence returned to the UI must retain verified classification/redaction
  assertions and existing native-link restrictions.
- No arbitrary provider URL, raw query, diff, log body or source payload is
  accepted through an incident mutation.
- Timeline events never include credential-bearing request envelopes or raw
  database errors.
- Incident writes do not call external integrations and do not execute Actions.

## 12. Compatibility and migration

The current Sprint 1 `Incident`, status, severity and disposition types are not
yet persisted or exposed as a production IPC surface. Sprint 15 may therefore
add explicit wire annotations and required fields without a data migration for
existing Incident rows.

The Sprint 11 `IncidentQueueItem` remains a read-only source projection. It is
not renamed or silently reinterpreted as the canonical Incident. The Sprint 12
topology filter continues to accept queue-item IDs until Sprint 16 deliberately
reconciles that UI surface. Sprint 13 CorrelationCandidate remains a candidate,
and Sprint 14 ChangeAssociation remains structural context rather than proof of
cause.

TypeScript receives canonical Incident types and guards, but no Sprint 15 view
is mounted. This gives Sprint 16 a tested contract without pulling its UX into
this sprint.

## 13. Testing

### 13.1 Domain tests

- table-driven allowed and rejected lifecycle edges;
- required context for each target status;
- reopen only from Monitoring, Resolved or Closed;
- Business Impact severity derivation and safety floors;
- severity override attribution;
- disposition independence and Duplicate reference rules;
- role cardinality and multi-role Principals;
- scope and trigger invariants; and

### 13.2 Repository and migration tests

- migration applies once and preserves existing databases;
- creation writes aggregate, triggers, roles and timeline atomically;
- rollback leaves neither current state nor orphan audit rows;
- request retry returns the original result;
- conflicting duplicate request is rejected;
- stale `expected_version` cannot overwrite a newer mutation;
- concurrent sequence allocation stays unique and ordered;
- timeline UPDATE/DELETE is rejected;
- workspace-constrained reads cannot leak another workspace; and
- role replacement/release history remains reconstructable.

### 13.3 IPC tests

- exact command, capability, scope and permission contracts;
- Owner/Administrator/Operator write access;
- Viewer/Auditor write denial and authorized reads;
- authorization before target/source existence disclosure;
- policy denial before persistence;
- exact-key and bounded-pagination validation;
- typed domain-to-IPC errors; and
- stable Rust/TypeScript contract alignment.

### 13.4 Acceptance fixtures

Committed deterministic fixtures demonstrate explicit creation from each of
the six source kinds. At least one Incident begins with multiple selected
source-backed triggers from an existing correlation candidate, while the
candidate itself is never stored as the trigger.

The acceptance path progresses an Incident through:

```text
Detected -> Triage -> Investigating -> Mitigating -> Monitoring -> Resolved -> Closed
```

It separately verifies:

- Monitoring, Resolved and Closed reopening paths;
- all four SCRUM-23 dispositions plus retained Informational compatibility;
- S1/S2 responder-role assignments;
- a rejected invalid edge and missing transition context;
- an atomic policy or source-resolution failure;
- optimistic-concurrency rejection; and
- an ordered actor-attributed timeline matching every accepted mutation.

### 13.5 Release gates

All seven gates must pass from the implementation branch:

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
npm run format:check
npm run lint
npm run typecheck
npm test
```

Run `npm ci` before frontend gates when dependencies are absent. A gate that
cannot run is blocked, not passed.

## 14. Acceptance statement

Sprint 15 is complete only when a permitted responder can explicitly create a
persisted canonical Incident from every supported source kind, can advance and
reopen it only through the accepted state machine with required context, and
can retrieve an immutable ordered timeline that attributes every accepted
change. Automatic creation, provider writes and the full Incident Workspace
remain absent.
